# Модель угроз по методике STRIDE: Банк (Цифровой город)

**Модель:** Claude Sonnet 5.5, веб-чат claude.ai
**Район:** Банк (d4-bank)
**Промпт:** единый промпт Л1 с описанием Банка (без уточняющих запросов)

> **Чего я не знаю о сервисе.** Не указаны СУБД, брокер Транспорта (RabbitMQ или Kafka), библиотеки API и то, есть ли в API ORM. Неизвестно, как Шлюз передаёт токены в API. До недели 4 аутентификации по документу «Архитектура города v0» ещё нет, поэтому меры с токенами OIDC и mTLS описывают целевую картину. Подпись и защита от повтора событий появятся только на неделе 5.

## 1. Элементы DFD

1. **Житель, кассир, администратор** — внешний участник (приходит через Шлюз).
2. **Паспортный стол** — внешний участник (выдаёт токены OIDC).
3. **HTTP API** (`api.bank.city.lab`) — процесс.
4. **Обработчик событий** — процесс (принимает `fee.requested`, публикует `fee.paid`).
5. **База данных** (счета, журнал двойной записи) — хранилище.
6. **Шлюз → API** — поток (HTTPS, токен OIDC в заголовке Authorization).
7. **Транспорт ↔ Обработчик** — поток событий (`city.cityhall.fee.requested.v1`, `city.bank.fee.paid.v1`).
8. **API и Обработчик → SOC** — поток журналов (JSON Lines из stdout).

## 2. Таблица угроз

| № | Элемент | STRIDE | Угроза | Мера защиты |
| :-: | :--- | :-: | :--- | :--- |
| K1 | Житель, кассир, администратор | S | Украденный токен OIDC позволяет переводить деньги от имени жителя. | Короткий срок жизни токена с проверкой `exp`, лимит на сумму и повторное подтверждение для крупных переводов. |
| K2 | Житель, кассир, администратор | R | Клиент отрицает перевод, а в журнале не видно, кто и откуда его отправил. | Для каждого перевода писать в журнал операций и в журнал SOC `actor`, `src_ip`, `request_id` и событие `data.change`. |
| K3 | Житель, кассир, администратор | E | Кассир единолично правит баланс или отменяет операцию и выводит деньги себе. | Корректировка только отдельной сторно-проводкой с подтверждением второго сотрудника и событием в SOC. |
| K4 | Паспортный стол | S | При компрометации ключа подписи Паспортного стола атакующий выпускает токен с ролью «администратор». | API проверяет подпись, `iss`, `aud`, `exp` и берёт роли только из проверенного токена; действия администратора пишутся как `admin.config.change`. |
| K5 | HTTP API | E | Подмена `account_id` в запросе: житель переводит с чужого счёта или читает чужую историю. | Владелец счёта определяется на сервере по `sub` из проверенного токена, `account_id` из тела запроса не считается доказательством прав. |
| K6 | HTTP API | T | Отрицательная, нулевая, дробная или огромная сумма в JSON (например, `"amount": -100`). | Валидация по схеме OpenAPI: целое положительное число копеек не больше лимита, плюс `CHECK` в БД. |
| K7 | HTTP API | T | Два параллельных перевода одновременно проходят проверку баланса, и счёт уходит в минус. | Проверка и списание в одной транзакции с блокировкой строки счёта (`SELECT ... FOR UPDATE`) и `CHECK (balance >= 0)`. |
| K8 | HTTP API | T | SQL-инъекция через параметры запросов к API. | Параметризованные запросы и отдельная учётная запись БД без прав на DDL и чужие таблицы. |
| K9 | HTTP API | I | Сообщение об ошибке раскрывает SQL-запрос, стек вызовов или версии библиотек; `/health` отдаёт лишнее. | Ошибки в формате RFC 9457 без деталей, `/health` возвращает только `{"status":"ok"}`. |
| K10 | HTTP API | E | Обход Шлюза: из другого района или из VPN обращаются прямо к порту API. | Порт API доступен только Шлюзу, между сервисами mTLS, в Compose не публикуются лишние порты. |
| K11 | HTTP API | D | Поток запросов или тяжёлые выборки по журналу операций исчерпывают соединения с БД. | Ограничение частоты запросов на Шлюзе и в API, пагинация и таймауты запросов к БД. |
| K12 | Обработчик событий | S | Поддельное `fee.requested` от имени Мэрии приводит к списанию денег с жителя. | Проверка mTLS-сертификата отправителя и `source` события; подпись добавится на неделе 5, до этого записать как открытую угрозу. |
| K13 | Обработчик событий | T | Повторная доставка того же `fee.requested` приводит к двойному списанию. | Таблица обработанных `id` событий с `UNIQUE`, запись в одной транзакции со списанием. |
| K14 | Обработчик событий | D | «Ядовитое» событие с неверным форматом роняет обработчик и блокирует очередь. | Валидация по JSON Schema, лимит повторов, отправка в очередь недоставленных Транспорта, `event.rejected` в журнал. |
| K15 | База данных | T | Прямое изменение баланса или стирание записей журнала в обход API. | Отдельные учётные записи для API и Обработчика, на журнал только `INSERT`, сверка баланса с суммой проводок, цепочка хэшей записей. |
| K16 | База данных | I | Дамп или резервная копия базы попадает посторонним. | Шифровать резервные копии, пароли и ключи хранить в `.env` вне Git, ограничить права на файлы. |
| K17 | Поток событий | I, T | Перехват или подмена `fee.paid` на пути к Мэрии. | mTLS до брокера, подпись события на неделе 5, в `data` только идентификаторы (`payer: user:ivanov`). |
| K18 | Поток журналов | R | Атакующий, захвативший контейнер, стирает локальные журналы, чтобы скрыть следы. | Писать в stdout и сразу отправлять в SOC, единственную копию в контейнере не хранить. |

## 3. Три самые опасные угрозы

1. **K5: подмена `account_id` (чужой счёт).** Это прямой путь к краже денег рядовым пользователем без каких-либо навыков: достаточно поменять одно поле в запросе. Ошибку легко допустить, потому что проверка токена проходит успешно, а проверка прав на конкретный счёт забывается.
2. **K12 и K13: поддельное или повторное событие `fee.requested`.** Конверт события пока без подписи и без защиты от повтора (по документу это неделя 5). Любой, кто может писать в шину, способен вызвать списание, а штатный повтор доставки списывает деньги дважды.
3. **K6 и K7: нарушение целостности денег (отрицательные суммы и гонка).** Банк хранит чужие деньги, поэтому ошибка здесь превращается в прямой финансовый ущерб и ломает инвариант двойной записи (сумма дебетов равна сумме кредитов). Оба дефекта типичны и проявляются не в обычной работе, а только при целенаправленной атаке.
