# Модель угроз по методике STRIDE: Платёжный сервис города (Банк)

> **Дисклеймер:** Инженеру по безопасности неизвестны точные СУБД (PostgreSQL, MySQL и т.д.) и технология шины событий (Kafka, RabbitMQ), а также то, проверяет ли Шлюз OIDC-токены самостоятельно или проксирует их в API. В мерах защиты используются стандартные паттерны для ACID-СУБД, брокеров сообщений и mTLS.

---

## 1. Элементы схемы потоков данных (DFD)

1. **Пользователи (Клиент, Кассир, Админ)** — внешний участник.
2. **HTTP API (`api.bank.city.lab`)** — процесс.
3. **Обработчик событий** — процесс.
4. **База данных (счета, журнал)** — хранилище.
5. **Шина Транспорта** — внешний процесс/среда.
6. **Мэрия** — внешний участник.
7. **Паспортный стол** — внешний участник.

## 2. Таблица угроз по методике STRIDE

| Элемент DFD | STRIDE | Угроза (конкретно для сервиса) | Мера защиты |
| :--- | :---: | :--- | :--- |
| **Пользователи** | **S** | Злоумышленник подменяет идентификатор клиента в HTTP-запросе для доступа к чужому счету. | Шлюз и API строго валидируют `sub` (subject) внутри OIDC-токена и сверяют его с mTLS-сертификатом сессии. |
| | **T** | Клиент изменяет сумму перевода или ID получателя в теле HTTP-запроса до отправки. | API валидирует все входные JSON-поля по строгой схеме (JSON Schema) и бизнес-логике перед выполнением. |
| | **E** | Обычный клиент подделывает claims в OIDC-токене, чтобы получить права кассира или администратора. | API проверяет криптографическую подпись токена на стороне Паспортного стола и жестко маппит роли (RBAC). |
| **HTTP API** | **T** | Атакующий компрометирует контейнер API и внедряет бэкдор для скрытого списания средств. | Контейнеры запускаются с read-only rootfs, от имени non-root пользователя и используют подписанные образы из доверенного реестра. |
| | **R** | Клиент отказывается от факта совершения платежа, утверждая, что операция не проводилась. | Каждая операция атомарно пишется в журнал двойной записи, а хэш транзакции дублируется в неизменяемые логи Городского SOC. |
| | **I** | В JSON-логах для Городского SOC случайно оказываются точные балансы счетов или ПДн клиентов. | На уровне API внедрен middleware для автоматического маскирования (data masking) финансовых данных и ПДн перед логированием. |
| | **D** | Злоумышленник отправляет миллионы запросов на перевод, исчерпывая пул соединений API. | На уровне Шлюза настроен rate-limiting на одного пользователя (по OIDC `sub`) и WAF для отсечения аномалий. |
| **Обработчик событий** | **S** | Обработчик принимает поддельное событие `city.cityhall.fee.requested.v1` от имени Мэрии. | Обработчик принимает события только по защищенному mTLS-каналу и проверяет цифровую подпись события от Мэрии. |
| | **T** | В событии от Мэрии передается отрицательная сумма комиссии, что приводит к начислению средств клиенту. | Обработчик отбрасывает события, где сумма (`amount`) не является строго положительным целым числом (копейки > 0). |
| **База данных** | **T** | Атакующий, получив доступ к БД, напрямую меняет баланс счета в обход бизнес-логики API. | Доступ к БД разрешен только сервисным аккаунтам API/Обработчика по mTLS; балансы хранятся в копейках (BIGINT) с защитой от переполнения. |
| | **I** | Злоумышленник читает дамп базы данных или резервную копию, получая все счета города. | Включено шифрование данных на.rest (TDE) с хранением ключей в внешнем KMS, а бэкапы шифруются на уровне приложения. |
| | **D** | Журнал операций двойной записи разрастается до исчерпания дискового пространства, БД падает. | Настроен автоматический архивный перенос (partitioning/purging) старых записей журнала и алертинг в SOC на заполнение диска. |
| **Шина Транспорта** | **T** | Атакующий перехватывает и изменяет событие `fee.paid` по пути к другим сервисам города. | События шифруются и подписываются на уровне приложения (end-to-end) до публикации в шину, а не только на уровне транспорта. |
| | **R** | Сбой в шине приводит к повторной доставке одного и того же события `fee.requested`, списывая комиссию дважды. | Обработчик событий использует ключи идемпотентности (idempotency keys) и сохраняет ID обработанных событий в БД. |
| | **I** | Злоумышленник с доступом к шине Транспорта читает названия улиц и суммы, восстанавливая финансовую карту города. | Полезная нагрузка (payload) событий шифруется симметричным ключом, известным только Банку и Мэрии. |
| **Мэрия** | **S** | Злоумышленник имперсонирует Мэрию и массово рассылает фиктивные запросы на списание комиссий. | Мэрия аутентифицируется в Шине и Банке через строгий mTLS (клиентский сертификат) и отдельный OIDC Client Credentials. |
| **Паспортный стол** | **S** | Компрометация Паспортного стола позволяет выпустить валидный OIDC-токен с ролью «администратор» для атакующего. | Паспортный стол использует короткоживущие токены (5-15 мин), строгую ротацию refresh-токенов и аппаратный MFA для своих админов. |

## 3. Топ-3 самые опасные угрозы

### 1. Нарушение идемпотентности при обработке событий (Replay в Шине/Обработчике)
* **Класс STRIDE:** Replay (в рамках Spoofing/Tampering контекста шины)
* **Обоснование:** Поскольку Банк реагирует на асинхронные события от Мэрии (`fee.requested`), любой сбой в сети или брокере сообщений может привести к повторной доставке (duplicate delivery) одного и того же события. Если Обработчик не реализует строгую идемпотентность (проверку `event_id` в БД перед транзакцией), с клиента спишут комиссию дважды или трижды. Это прямая финансовая потеря и разрушение доверия к сервису.

### 2. Race Condition (TOCTOU) при выполнении переводов (Tampering/Логика в API)
* **Класс STRIDE:** Tampering
* **Обоснование:** Если API проверяет баланс клиента (`SELECT balance`), а затем списывает средства (`UPDATE balance`), не используя строгие блокировки (например, `SELECT ... FOR UPDATE` в PostgreSQL) или ограничения уровня БД, два параллельных запроса от клиента (или бэкдора) могут пройти проверку баланса одновременно. Это классическая уязвимость double-spending, которая позволяет уйти в минус и нарушить принцип двойной записи (сумма дебета и кредита по городу не сойдется).

### 3. Манипуляция с типами данных и знаками сумм (Tampering в API/Обработчике)
* **Класс STRIDE:** Tampering
* **Обоснование:** Деньги хранятся целыми числами в копейках. Если API или Обработчик событий не валидируют жестко тип данных и знак числа, атакующий может передать в JSON отрицательное значение (например, `"amount": -50000`) или число, вызывающее переполнение (если используется 32-битный `INT` вместо `BIGINT`). Отрицательный перевод фактически зачислит средства на счет клиента из воздуха, а переполнение сломает математический баланс двойной записи, что критично для финансового ядра.
